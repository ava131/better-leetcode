# AI 刷题小助手 — 产品需求文档

> 状态：**待评审**（尚未开工）
> 版本：v0.1 · 2026-09-16
> 评审人：用户本人（唯一用户 + 唯一决策者）

---

## 1. 背景与问题

### 1.1 真实卡点

刷题时的困难**主要不在"想不到解法"**，而在"想到了、也写出来了，但细节不对"：

- `cur.next` 该指向谁
- `[left, right]` 该不该 `+1`
- 去重时 `while` 的边界条件

这类卡点的特征：

1. **自己看不出来** —— 在脑子里模拟指针/下标执行不可靠，链表尤其不可靠
2. **或者要花很久** —— 盯着一行看半小时
3. **粒度极小** —— 是"第 3 步"，不是"第 1 章"

### 1.2 现有资源为什么不够

| 资源 | 缺口 |
|---|---|
| **官方题解** | 预设读者已懂 → 看不懂；抽象（讲"收缩区间"，不讲"这里 `+1` 没"）；**固定文本，不看你的代码**；从"思路"直接跳到"正确代码"，中间的"你这一步为什么错"被整个跳过；给了也不说为什么 |
| **官方 Leet 智能助手** | 2026.3 上线的「提交结果分析」是**回头看的总结**（思路对比/复杂度/代码质量）；2026.5 的 Quick Fix 是修编辑器报错。都不是"陪你走一遍" |
| **第三方插件** | 调研 400+ 个仓库/产品，绝大多数是"题面 + 你的代码 → LLM 解释"，**不接触判题输出**；做得最认真的 [PatternCoach](https://github.com/Iriss0904/personalized-leetcode-coach) 也只有 23★ |

### 1.3 一个被验证过的结论

调研发现（详见 `research/ai-leetcode-tools.md`）：

- **做得最好的实现，拿到最少的用户**（23★）。官方已把"提交结果分析"内置并捆绑 Plus
- 因此**本产品不以"做产品"为目标**，目标是**自己每天真的会用**

## 2. 目标与非目标

### 2.1 目标

**把"把代码扔给 LLM 新窗口"这件事，变成一个不用搬东西、还带记忆的动作。**

现状的问答流程是 6~7 步：

> 切窗口 → 复制题面 → 复制代码 → 复制报错 → 粘贴 → 打字描述困惑 → 追问

**本产品要把它压到 1~2 步。** 能力上不比新开一个窗口能做更多 —— 只是**不用你搬**。

可衡量的目标（只有一条）：

> **下次卡在 `cur.next` 上时，第一反应是打开它，而不是去点题解。**

### 2.2 非目标（本期不做）

- ❌ 题库、题目管理、刷题计划、打卡
- ❌ 判题器。**不自己判题**，只读 LeetCode 已有的判题结果
- ❌ **代码选区功能**。整份代码直接进上下文，不做"选中某几行"（理由见 FR-1）
- ❌ **保存对话历史**。只沉淀结构化结论（理由见 FR-5）
- ❌ 自动提交、自动改代码、自动写回编辑器
- ❌ 多用户、云同步、账号体系、分享
- ❌ 移动端、Firefox、Edge
- ❌ 把 AI 做成"克制不给答案"的导师。**要的是直接好用的助手**，追问能力由对话本身提供

## 3. 用户与场景

### 3.1 用户

只有一个人：**会写代码、自己在 LeetCode 上刷题、且坚持自己写代码（不看答案抄）** 的开发者。

这决定了几个前提：

- 用户**自己会写**是产品成立的前提（否则没有"我的代码"可分析）
- 用户**能判断 AI 说的对不对** —— 这是本产品最重要的一条假设，见 §9
- 不需要考虑陌生人上手、onboarding、教程

### 3.2 典型场景

**场景 A · 提交后复盘**

> 提交，WA。侧边栏已经自动加载了这份代码和失败用例。用户问"哪里错了"，AI 直接指出第 7 行 `left = mid` 会死循环。用户追问"为什么不改成 `mid+1` 就死循环"，AI 解释。用户问"那这题有几种做法"，AI 讲思路 + 复杂度。

**场景 B · 提交前卡住（最高频）**

> 代码写到一半，觉得去重那几行不对。直接打字问"去重那段是不是有问题"——不用说是哪几行，整份代码已经在 AI 手里了。用户再要求"给我一个小例子一步步走"。

**场景 C · 改对了，但想知道刚才那版为什么错**

> 改完提交，AC 了。用户问"刚才那版为什么错"。AI 能拿到**上一次提交的代码**（插件天然存着，手动复制粘贴做不到这件事）。

**场景 D · 跨题回顾（长期）**

> 攒了三十道题之后，问"我是不是老在边界条件上错"、"三数之和这题有几种解法，我会几种"。

### 3.3 明确要保住的东西

> **看一个 bug 的过程才是最重要的步骤。**

学习发生在"看见自己错在哪一步"的那一刻，不在拿到正确解法的那一刻。产品设计不能为了"给答案快"而牺牲这个过程的可展开性。

## 4. 需求

### FR-1 · 上下文自动就位

**上下文只需要三样东西**：

| 上下文 | 来源 | 时机 |
|---|---|---|
| **题干** | GraphQL `questionContent` / DOM | 进页面时 |
| **用户的代码（整份）** | 编辑器实时内容 | 每次改动（防抖） |
| **一个测试用例** | 提交后：LeetCode 的失败用例<br>运行后：示例用例的逐条对比<br>提交前：留空，或让 AI 造一个最小的 | 提交 / 运行后自动 |

就这样。**不要**那一堆判题元数据（"通过 311/313"、击败百分比、内存分布）—— 对"弄明白这段代码"没有帮助，只是噪声。唯一值得带的是**判定结果本身**（WA / TLE / RE）一行，以及 RE 时的报错信息。

**为什么代码不需要"选区"**：LeetCode 的解法就二三十行，**整份塞进去完全不占地方**。省 context 是个伪需求，而"先选中某几行"反而多一步操作。
用户想说"去重那段有问题"，用自然语言说就行 —— 全文已经在 AI 手里了。

**代码只有一个来源，但要避开一个坑**：抓**编辑器的真实内容**，**不要**抓 Monaco 渲染出的 `view-lines` DOM —— 那会丢缩进和换行。现有插件（如 LeetcodeDebugAssistant）都在犯这个错。

---

### FR-2 · 提问入口（"更快更方便"的落点）

**两个入口就够**（原设计的"代码选区浮动按钮"已砍掉，见 FR-1）：

| 入口 | 交互 | 对应意图 |
|---|---|---|
| **常驻右侧边栏**（可一键收起） | 随手打字 | 主要入口 |
| **快捷键唤起输入框** | 不打断编辑，手上正在打字时用 | 次要入口 |

**核心洞察**：真正的摩擦不是"AI 答得慢"，而是**"你要用语言描述你的困惑"** —— 很多时候描述不出来，只能说"就是感觉不对"。

所以降低表达成本的方向是**让上下文替你把话说一半**：题干和代码已经在 AI 手里了，你只需要说"这版哪错了"、"去重那段是不是有问题"——**指代靠自然语言，不靠选中操作**。

**辅助**：侧边栏给几个**建议问题 chip**（"这版哪里错了"、"为什么这里要 +1"、"有几种解法"），点一下就发，**零打字**。

**必须有的指示器：上下文状态条**

因为 LLM 是无状态的（§8.1），用户**看不见插件到底准备好了什么**。所以输入区上方常驻一条状态条：

| 状态 | 显示 | 含义 |
|---|---|---|
| 灰 | `○ 已就绪（未提交）· 环形链表 · 题干 + 代码` | 能问思路，但没有判题结果 |
| **蓝** | `● 判题中…` （脉冲动画） | 已提交，等力扣判完（判题是异步的） |
| 绿 | `● 上下文已就绪 · Wrong Answer · 17/29` + 失败用例 | **判完自动变绿**，AI 能看到失败用例 |
| 黄 | `⚠️ 判题结果未取到` / `⚠️ 后端未连接` | 取数失败，退化或提示 |

提交后这条会从灰变绿，**这就是"提示我上下文已就绪"**。它同时起到三个作用：告诉用户准备好了、告诉用户准备好了什么、失败时不让用户误以为 AI 什么都知道。

---

### FR-3 · 对话能力（基础功能，不做特化）

以下都是普通 chatbot 就该有的，**不需要专门设计**，但必须在：

- 讲思路
- 分析时间/空间复杂度
- 回答"为什么这样""为什么不那样"
- 贴正确代码（要就给，不藏着）
- 多轮追问

**唯一的要求是"具体到行"**：题解只能说"注意边界"，本产品必须能说"第 7 行 `left = mid` 少了个 `+1`"。**这是相对题解唯一的实质优势。**

---

### FR-4 · 逐步调试（FR-3 里的一种动作）

用户说"找个用例一步步走"时：

1. 挑一个**最小的、能踩到这个坑的**输入 —— 越简单越好，小到用户能在脑子里跟住
2. **逐步展开变量** —— 每步只列相关的那几个，不 dump 整个状态
3. **走到出问题的那一步停下来**
4. 让用户自己先看一眼

**输出形态**：对话 + 一张逐步的变量表。**不是一份长报告** —— 用户要的是"一点一点"，不是文档。

**上下文里的判题失败用例**在这里直接复用：如果失败用例本身已经足够小，就拿它当输入，不用另造。

---

### FR-5 · 存什么、不存什么

> **v0.7 反转了这条**。原设计是「只存结构化事实（卡点/掌握度），不存对话」。
> 反转的理由：**很多思路是在对话里诞生的**，摘要会把过程丢掉；而且
> 「结构化记忆」是模型建议的，幻觉重灾区（我们为它修过 `<memory>` 泄露的 bug）。

| | 存不存 | 说明 |
|---|---|---|
| **对话（用户 + 助手正文）** | ✅ **全量存** | 有对话就存 |
| **模型的思考过程** | ❌ 不存 | 那是模型的推理不是用户的思路，且占 ~85% 体积 |
| **每轮的上下文快照** | ✅ 存 | 当时的代码/判定/用例。**只在变化时写**（去重） |
| 题干 / 测试用例本身 | ❌ 不存 | 每次现取，不值得存 |
| ~~卡点表 / 掌握度矩阵~~ | ❌ **已废弃** | 见下方说明 |

**为什么丢掉「结构化记忆」**：那是**平行维护**的第二份事实来源，两份就有不一致的风险，
而且那份还是模型建议的。现在有了全量对话 + 检索，那些结论**可以随时现推**：

| 以前要维护 | 现在 |
|---|---|
| 卡点表 | 搜「边界」→ 命中所有相关对话 |
| 掌握度矩阵 | 问「三数之和我会几种解法」→ 它翻历史回答 |
| 认知归因 | 事后从对话提炼（比实时提准得多） |

**需要就推，不需要就不推。** 顺手也删掉了一整类代码（`<memory>` 块、确认卡片、
`/memory/confirm`、两张表、prompt 注入）。

**体积实测**（`node:sqlite`，中文 3 字节/字）：

| | 每轮 | 每天 15 轮 | 一年 |
|---|---|---|---|
| 只存正文 | ~3.3 KB | 50 KB | **18 MB** |

**不压缩。** gzip 能省 3~4 倍，但压缩后**没法检索**——而检索是这件事的全部价值。

**检索**：用 `LIKE`，不用 FTS5。实测 FTS5 的 `unicode61` 分词器把**连续中文当成一个 token**，
搜「边界」在「注意闭区间的边界处理」里命中 0 条；`trigram` 又要求 ≥3 字符。
`LIKE` 对中英文一视同仁，也没有特殊字符的语法错误。这个规模全表扫是毫秒级。

### FR-6 · 历史标签（本期）

侧边栏加一个 **「历史」标签**：

- **只有存在历史对话时才显示**。新题跟以前一模一样，不显示这个标签
- 列出这道题的历史会话（时间 / 条数 / 首条用户消息），**最近的在前**
- 点进去 = **只读回看**，包含当时的代码快照（可展开）
- 每条右边有 **「继续这条对话」**，点了载入到当前对话接着聊
- 顶部一个搜索框，**只搜当前这道题**（跨题搜索等攒够题量再做）

**重开一道有历史的题，默认是空白对话 + 历史标签**（不是自动载入上次的上下文——
那个上下文里还有上次的错误代码，容易污染）。

### FR-7 · 分层导师（P2，本期不做）

> 想法由用户提出，**现在不做，记在这里**。理由见下。

两层结构：

1. **单题 agent**（现有）：聊完一道题后，写一份这题的总结（卡在哪、怎么一点一点纠正的）
2. **类型导师 agent**（新增）：收同类型题目的所有总结，**不直接和用户对话**，
   像老师/错题本一样在大的方向上归纳（"这类题你经常错在 X"），生成一份类型摘要
3. 那份类型摘要**回灌**给同类型的单题 agent

**为什么这个形状是对的**：每层只看下一层的浓缩，**上下文永远有界**。
50 道题的摘要 ≈ 10K 字，塞得下。而且它让"画像"在第 3~5 道题就开始有输出，
不用等 20~30 道。

**但四个问题必须先解决**（都不在代码上）：

| # | 问题 |
|---|---|
| 1 | **LeetCode 的标签是错的切分轴**。标签描述的是*题目*（数组/双指针），你要的导师描述的是*你的毛病*（边界条件/比较时机）。「环形链表」挂 4 个标签，你的毛病"比较放在移动之前"四个都不贴切。真正有用的切分是**错误模式**，但那个得从数据里长出来 |
| 2 | **会僵化**：改好的毛病还在被念。导师的输出必须每次**重写**（不是追加），而且要有"最近是否还出现"的概念 |
| 3 | **误差会累积，而且是闭环放大**：单题摘要错 → 导师结论错 → 回灌给单题 agent → 又写进下次摘要。而且导师**看不到原始对话，无法自我纠错** |
| 4 | **"聊完"没有定义**。今天聊一半明天接着聊，什么时候触发汇总？ |

**硬约束**：导师的每个结论**必须引用具体题目**（"见：环形链表、快乐数"），
否则你无法核对，问题 3 会失控。

**并且导师的输出要给人看**，不只是给 agent 看——**「错题本」是给用户看的**，
这才是主要收益。加一个只读的「我的弱项」页。

**为什么现在不做**：现在做等于**凭空猜**——切分轴、摘要粒度、触发点全都猜不出来。
先攒 30 道题的对话，翻一遍，**数据会告诉你正确的切分方式**，那时可能两小时就搭完。

**为了将来能做，现在有个约束**：对话存储里必须留着 `problem_id`，
`problems` 表里必须留着 `tags`。有了这两个，「按 tag 聚合所有摘要」就是一个 SQL 查询。
**不用现在设计导师，只要别把数据丢成聚不起来的样子。**

## 5. 关键技术事实

### 5.1 ★ 站点是 leetcode.cn（力扣），不是 .com

R0 实测（详见 `docs/R0-captured-api.md`）：用户浏览器里**只有 `leetcode.cn` 的登录态**，没有任何 `.leetcode.com` cookie。

这不是小事 —— `.cn` 与 `.com` 的接口不一样：

| 差异 | `.cn`（力扣） | `.com` |
|---|---|---|
| 提交详情字段 | **`submissionDetail`（单数）** | `submissionDetails`（复数） |
| 提交历史 | `GET /api/submissions/` | `GET /api/submissions/` |
| CSRF | **必须带 `x-csrftoken`** | `/graphql/` 只需 cookie |

### 5.2 实测结论（R0，全部已验证）

| 事项 | 结论 | 状态 |
|---|---|---|
| **失败用例（R1）** | ✅ **免费用户能拿到完整用例**：`outputDetail.input` / `codeOutput` / `expectedOutput`，**无截断、无占位** | ✅ 实测 |
| 提交详情 | `POST /graphql/`，operationName `submissionDetails`，字段 `submissionDetail(submissionId: ID!)` | ✅ 实测 |
| `outputDetail` 位置 | 挂在 `GeneralSubmissionNode` / `ContestSubmissionNode` 上，**必须写 `... on` 内联片段** | ✅ 实测 |
| 代码来源 | `submissionDetail.code` = **完整带缩进的权威副本**（判题时真正跑的那份） | ✅ 实测 |
| 题干 | `POST /graphql/` operationName `questionDetail`，取 `translatedContent`（中文 HTML） | ✅ 实测 |
| 提交历史 | `GET /api/submissions/?offset=&limit=` → `{submissions_dump, has_next, last_key}` | ✅ 实测 |
| 鉴权 | `x-csrftoken` 必需；且 **`csrftoken` cookie 可从 `document.cookie` 直接读**（非 httpOnly） | ✅ 实测 |
| 会员门槛 | 实测账号 `isPremium: false`，全部字段可读 → **无门槛** | ✅ 实测 |
| MV3 取数 | `world:"MAIN"` 包装 `fetch`/`XHR`（`run_at:"document_start"`，Chrome 111+）；MAIN world 无 `chrome.*`，需 `postMessage` 转 ISOLATED | ✅ 文献 + 设计 |
| 限流 | `.cn` 社区报告约 60 次/10 分钟，**未压测**。设计上每次提交只增加 **1 个**额外请求 | ⚠️ 未压测 |
| 提交端点（R3） | 未实测（**故意**：提交会写账号记录）。`.com` 真实抓包显示是 REST `POST /problems/{slug}/submit/` | ⚠️ **实现时按 URL 模式泛化匹配，不写死** |

### 5.3 官方 AI 的能力边界（R0 实测字段）

抓到官方 `submissionAnalysis` 的完整字段：复杂度分析、`efficiencyImprovements`、**`readabilityScore` / `structureScore`（评分）**、`styleImprovements`、`currentKnowledge` / `suggestedKnowledge`（知识点映射）、`coreConcept`、`guidanceQuestion`。

**结论**：官方产出的是**评分式复盘总结**，形态是一份报告 —— **不是陪你逐步调试**。

另外实测 `submissionAnalysisUsesLeft: 1`：免费账号额度极小，基本不可用。


**重要**：本产品**只用** LeetCode 的判题**结果**，不提交代码、不模拟提交。所有请求都是读，且**只在用户主动操作时触发**。这既降低风控风险，也避免与官方判题产生任何冲突。

## 6. 架构

### 6.1 组件

```
┌─────────────────────────── Chrome ───────────────────────────┐
```

### 6.2 为什么用本地后端（已拍板）

| 理由 | 说明 |
|---|---|
| **API key 不进浏览器** | 放 `.env`，扩展永远拿不到 |
| **记忆不绑浏览器** | SQLite 在磁盘上，重装扩展/换浏览器不丢。`chrome.storage` 会被清、有容量限制、后端无法聚合 |
| **能换模型、能看日志** | 调 prompt 时必须能看到"实际发出去的是什么" —— 这是本产品的核心工作流 |
| **能记 token 成本** | 每次调用记 token/延迟/费用，避免用着用着不知道花了多少 |

### 6.3 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端运行时 | Node 24 | 自带 `node:sqlite`（**零原生依赖**）和 TS 直跑（**零构建步骤**） |
| 后端框架 | Hono（或裸 `node:http`） | 轻，够用 |
| 扩展框架 | WXT 或裸 Vite + MV3 | 需要 main world 注入 + HMR |
| UI | 原生 TS + Shadow DOM | **必须隔离样式** —— 否则被 LeetCode 的 CSS 污染 |
| 存储 | `node:sqlite` → 单文件 SQLite | 无服务、无迁移工具、可直接用 sqlite3 命令看 |
| LLM | OpenAI 兼容接口（可换 base_url） | 不锁厂商 |

## 7. 数据契约（扩展 ↔ 后端）

这是**最关键的接口**。后端不认识 LeetCode，只认识这个结构；扩展只负责把它填满。

```jsonc
{
  "problem": {
    "id": 15,
    "slug": "3sum",
    "title": "15. 三数之和",
    "difficulty": "Medium",
    "tags": ["数组", "双指针", "排序"],
    "content": "给你一个整数数组 nums ……"          // markdown
  },

  // 代码：整份，不截取。来源是编辑器真实内容
  "code": "class Solution:\n    def threeSum(self, nums):\n        ...",
  "lang": "python3",

  // 判题：有提交时才有。只要"判定 + 一个用例"，不要元数据
  "verdict": "Wrong Answer",                        // 或 null（提交前）
  "testcase": {
    "input":    "[-1,0,1,2,-1,-4]",
    "output":   "[[-1,0,1],[-1,-1,2],[-1,0,1]]",    // 你的输出
    "expected": "[[-1,-1,2],[-1,0,1]]"
  },
  "runtimeError": null,                             // RE 时填报错信息

  // 会话内存里的最近 2 份代码快照（不落库），见 §8.3
  "codeHistory": [
    { "code": "……v1……", "verdict": "Wrong Answer", "testcase": { } }
  ],

  // 后端从 SQLite 捞出来注入，见 §7.1
  "memory": {
    "stuckPoints": [ { "desc": "去重时 while 边界", "insight": "闭/半开区间语义不统一", "count": 3 } ],
    "approaches":  [ { "name": "排序+双指针", "mastered": true } ]
  }
}
```

**这个契约先冻结**，扩展和后端各自独立开发。

### 7.1 记忆部分的字段设计

记忆**不是**对话记录，是三类结构化事实：

```jsonc
// 卡点：这题我卡在哪
"stuckPoints": [
  { "desc": "去重时 while 的边界",
    "insight": "闭区间 / 半开区间语义没统一",   // 认知层归因，可为空
    "count": 3,                                // 出现次数
    "first": "2026-09-01", "last": "2026-09-16" }
]

// 解法掌握度：这题有几种解法，我会几种
"approaches": [
  { "name": "三重暴力",    "time": "O(n³)", "mastered": false },
  { "name": "排序+双指针", "time": "O(n²)", "mastered": true,
    "evidence": "2026-09-10 独立 AC" },       // 判定依据
  { "name": "哈希表",      "time": "O(n²)", "mastered": false,
    "note": "知道有，没写过" }
]
```

**没有对话表。** 会话内的对话是临时的，不落库（见 FR-5）。

## 8. 交互细节

### 8.1 核心机制：LLM 是无状态的

**必须先说清这一点**，否则整个交互模型会被误解。

LLM **不主动知道任何事**。它只在**一次调用发生的那一瞬间**才"知道"。

所以提交后真正发生的是：**上下文在本地备好了，但没有任何模型被惊动。** 用户在侧边栏发出第一句话时，插件才把 `当前上下文 + 对话历史` 打包发出去 —— 这时 LLM 第一次看到判定和失败用例。

> **插件不主动做任何事。它只保证：用户开口的那一刻，AI 已经知道他刚提交了什么。**

### 8.2 完整时间线

```
① 进题目页
   题干 ✓        代码开始实时同步 ✓        用例 ✗   判定 ✗
   → 这时就能问："这题有几种解法？""思路是什么？"

② 写代码
   代码静默同步进本地缓存（不发请求，不烧钱）

③ 点提交 → WA
   拦截 → submission_id → **轮询判题结果**（判题是异步的，见下）
   侧边栏状态条先进中间态：  🔵 判题中…（蓝，脉冲）
   判完（约 1~3 秒）→        🟢 上下文已就绪 · Wrong Answer · 17/29
   对话流插一行：            ──── 提交 #1 · Wrong Answer ────
   显示建议 chips：          [这版哪里错了] [为什么这里要 +1] [有几种解法]
   ✗ 此时 LLM 还不知道（没有任何调用）

   ⚠️ **判题是异步的**：submit 返回时 statusDisplay 还是空字符串。
      必须轮询到 verdict 非空，否则状态条永远不变。（实测 +0ms 为 ""，+2000ms 才是 "Wrong Answer"）
      中间态「判题中…」是必要的 —— 否则这几秒界面看起来是死的。

③' 或者：点「运行」（不提交，只跑示例用例）
   POST /problems/{slug}/interpret_solution/ → interpret_id
   轮询 /submissions/detail/runcode_.../check/ → 逐用例对比
   侧边栏状态条： 🔵 运行中… → 🟢 运行结果已就绪 · Accepted · 3/3
                 并显式标注「示例用例全过（但示例全过 ≠ 提交能过）」
   建议 chips 换成： [这个用例为什么不过] [运行过了为什么提交会挂] …

   ⚠️ **运行 ≠ 提交**：运行只跑题目自带的 2~3 个示例用例，通常很宽松。
      最常见的困惑就是「运行全过、一提交就 WA」。system prompt 里专门交代了这点，
      要求 AI 不许说「你的代码没问题」，而要去想示例用例覆盖不到什么。

④ 点 chip 或打字
   ★ 这一刻 LLM 才看到：题干 + 代码 + 判定 + 失败用例 + 问题
   → 它能直接说"第 7 行 left = mid 会死循环"，因为它手上有事实

⑤ 追问、要求"找个用例一步步走"
   正常多轮对话（FR-4）

⑥ 改代码 → 再提交
   见 §8.3

⑦ 换到另一题
   会话丢弃（不落库）
   但记忆（卡点 / 掌握度）跟着题目走，还在
```

### 8.3 再次提交怎么处理

**不清空对话。** 三种做法：

| 做法 | 评价 |
|---|---|
| ① 清空重来 | ❌ 丢掉刚问出来的诊断 |
| ② 把新代码作为一条 user 消息塞进对话 | ❌ 浪费（代码已在上下文里），且污染对话 |
| ③ **静默更新上下文 + 对话流插一行标记** | ✅ 采用 |

标记只有一行，**不重复贴代码**：

```
──── 提交 #2 · Accepted ────
```

**配套：会话内存里留最近 2 份代码快照（不落库）。**

理由：按"每轮只发当前快照"的设计，v1 的代码会被 v2 覆盖，于是这个场景会翻车 ——

> v1 → WA → 讨论一通 → 改成 v2 → AC → 问"**刚才那版为什么错**"

此时当前上下文是 v2（AC，没有失败用例），v1 的代码已不在。留 2 份快照即可支持。

这也是 **Q6 的最终答案**：上一版代码**留，但只留在会话内存**，不进数据库 —— 因为它的价值只在"同题 + 同会话 + 想对比版本"这个小窗口里。

### 8.4 消息结构

每次发问，后端实际拼出去的是：

```jsonc
{
  "messages": [
    { "role": "system",  "content": "<陪练 prompt>" },

    // ↓ 对话历史：只放"说过的话"和分隔标记，不放代码
    { "role": "user",      "content": "这版哪里错了" },
    { "role": "assistant", "content": "第 7 行 left = mid ……" },
    { "role": "system",    "content": "──── 提交 #2 · Accepted ────" },
    { "role": "user",      "content": "刚才那版为什么错" }   // ← 当前这句
  ],

  // ↓ 每轮重发的最新快照（不进 messages）
  "context": {
    "problem":  { },
    "code":     "……当前（v2）……",
    "lang":     "python3",
    "verdict":  "Accepted",
    "testcase": null,
    "codeHistory": [                       // 仅会话内存，不落库
      { "code": "……v2……", "verdict": "Accepted" },
      { "code": "……v1……", "verdict": "Wrong Answer",
        "testcase": { "input": "...", "output": "...", "expected": "..." } }
    ],
    "memory":   { }                        // 从 SQLite 捞，见 FR-6/FR-7
  }
}
```

**职责分离是重点**：

- `messages` 里**不放代码** → 代码变了不污染对话
- `context` 里**不放对话** → 对话变长了也不重复带代码（省 token）

提交分隔标记用 **system 角色**，让 AI 只当背景，不把它当提问来回应。

### 8.5 记忆确认卡片

AI 消息里返回的结构化记忆建议会被后端**剥离**，变成一张卡片：

```
┌─────────────────────────────────────┐
│ 💡 记下来？                          │
│ 卡点：双指针去重的 while 边界         │
│ 认知：闭区间 / 半开区间语义没统一      │
│              [ 记下来 ]  [ 不用 ]    │
└─────────────────────────────────────┘
```

用户点确认才写库。**原文不显示给用户**（避免污染阅读）。

### 8.6 会话边界

- 换题 → 自动开新会话（旧会话**不保存**，见 FR-5）
- 同题反复提交 → **同一会话** + 一行分隔标记（§8.3）
- 长会话 token 管理：`context` 每轮全量重发（题干 + 代码就几百 token，不值得为省它增加复杂度）；`messages` 只保留最近 N 轮
- 关掉侧边栏或换题 → 对话与代码快照全部丢弃。**想留的东西靠"记下来"卡片沉淀**（FR-6）

## 11. 验收标准

### 11.1 唯一北极星

> **下次卡在 `cur.next` 上时，第一反应是打开它，而不是去点题解。**

### 11.2 分阶段验收

| 阶段 | 通过标准 |
|---|---|
| M0 | 打印出的 prompt 让人看完觉得"AI 拿到这些应该能答好" |
| M1 | 拿一道**真实卡过的题**，回答比手动粘贴到 ChatGPT **明显更好或明显更省事** |
| M2 | 从"我卡住了"到"AI 看到全部上下文"≤ **2 个动作** |
| M3 | 问"刚才那版为什么错"能正确回答（这是手动流程做不到的） |
| M4 | 做完一道题，不点任何额外按钮，掌握度矩阵自动多出一条待确认项 |

### 11.3 明确的失败信号

出现以下任一情况，应当**停下来重新考虑设计**，而不是继续加功能：

- M1 之后，自己主动使用的次数 **< 每周 2 次**
- M2 之后，仍然觉得"直接开 ChatGPT 更快"
- 需要靠"更多功能"来说服自己这东西有用
